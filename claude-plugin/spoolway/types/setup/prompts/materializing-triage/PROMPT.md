# materializing-triage

## The lane environment

The harness sets the task's environment. A lane resumed after a dispatcher restart, a reboot or a
usage-limit stop can lose it, and an empty `$SPOOLWAY_SCRATCH` resolves to `/`. Before the first
use, restore it from the worktree and stop if that fails:

    . scripts/spoolway/lane-env.sh || exit 1

Every command that reads or writes the scratch space begins with that line, in its own shell.

The message that opened this lane started the `triage` skill. You triage one issue, the spec this
task is bound to, before any ticket is cut from it. Everything below narrows the skill to this
pipeline.

## What you are looking at

- `skip_steps` in the task file's frontmatter: if it names `triage`, change nothing and report a
  pass at once, ignoring the skill's text. Read this first.
- `ticket` in the frontmatter: the spec, and the only issue you triage. Read it live with
  `gh issue view <n> --json state,labels,body,comments`. If its live state contradicts the task
  body, block and say how.
- `$SPOOLWAY_SCRATCH/breakdown.md`: the breakdown the owner approved in the grill, and
  `## Handoff` in the task file: what the grill settled. If `breakdown.md` is missing or does not
  say the owner approved it, block: the grill did not finish.
- `docs/agents/triage-labels.md`: the label strings of this tracker.

## How to do it here

- Nobody is at the pane, and the grill already was the interview. Do the skill's "Triage a
  specific issue" on the spec without its waits: never ask for direction, never use
  AskUserQuestion, and never start another grill. Decide, and leave the choice as a handoff note.
- Run the skill's two codebase checks, redundancy and prior rejection, and say where you looked.
- The outcome for a spec that is about to be cut into tickets is one category label, `bug` or
  `enhancement`, and the state `ready-for-human`: a spec is delivered through its tickets, never
  handed whole to an agent. Take off any other triage state label (`needs-triage`, `needs-info`,
  `ready-for-agent`) and no other label: the `spoolway:` labels are the issue hook's. Post one comment on the spec in the
  shape of the skill's agent brief: what is established, the approved breakdown in short, and why
  the spec itself is not delegated.
- If the checks say otherwise, block and say why, and change nothing on the spec: it is already
  built, it was rejected before, or it cannot be specified without something only its author
  knows. `wontfix` and `needs-info` on a spec are the owner's to apply.
- The skill asks every comment to begin with a line saying it was generated by AI. This project
  carries no AI attribution anywhere: leave that line out, and name no tool or model as an author.
- A comment never carries a closing keyword before an issue: write `part of #N`, never close,
  fix or resolve followed by `#N`.

## If your report is refused

The command you finish with can itself be refused. When it says no task is given, the lane
environment is not set: source `scripts/spoolway/lane-env.sh` first, which infers the task id
from the worktree. Read what it printed, then run it once more with `-C "$SPOOLWAY_REPO"` right
after `spoolway` and the same flags. If that is refused too,
stop: make your last message the refusal and the command you ran, change nothing else and end
your turn. A person reads the pane. Never work around a refusal, and never ask another session
for help.

## Never

- Never triage, label or comment on any issue but the spec. Never close the spec or edit its body.
- Never open an issue. Never write to `.out-of-scope/`.
- Never edit a file in the repository. The one pull request of this pipeline holds what the
  `document` step writes and nothing else, and a commit made here would be squashed into it. What
  a file should say goes in a handoff note.
- Never create `docs/adr/` or any other decision directory, and never write under the pages directory `.spoolway/companion.env` names.
- Never contact another session: no SendMessage, no ListAgents, no herdr or tmux command, no
  other lane's pane.
- Never touch the queue, and never edit the task file: the report you finish with is the only
  thing that writes to it.
- Never run a deploy, a release or device command, or anything that reads or writes a secret.
- Never leave what a person needs in your scratch space alone: it is deleted when the task ends,
  and a note that only names a file there tells nobody anything. Write the text itself in a
  handoff note; when it is too long, its actionable part and then the file's name.
